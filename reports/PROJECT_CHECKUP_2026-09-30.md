## Найденные проблемы

Все пункты ниже уровня P2: исправить в обычном цикле разработки. Пункты 1–3 наиболее важны для повседневной работы. P0/P1 с доказанным аварийным ущербом не найдено.

### 1. Восстановленная позиция трека сбрасывается перед Play

**Место:** [player.tsx](F:/Spotify-Like/src/player.tsx:113), восстановление на строках 126–134, запуск на строках 143–150.

Восстановление записывает сохранённую позицию в `statusRef`, но не загружает трек в аудиодвижок. Каждые 400 мс обычный опрос получает от пустого движка `id: null`, `position: 0`, `duration: 0` и полностью заменяет восстановленный статус. Затем Play берёт позицию уже из этого обнулённого объекта.

**Доказательство:** скрипт проверки выполняет настоящий `usePlayer` через минимальный mock React/IPC. Сессия восстанавливается на 75 секунде; один вызов штатного polling переводит позицию в 0; Play не отправляет `seek`. Это воспроизведение логики hook, не живой тест WebView.

**Последствие:** продолжение прослушивания после перезапуска начинается с начала. До запуска также пропадает восстановленная длительность.

**Исправление:** хранить позицию ещё не загруженной сессии отдельно от статуса движка либо сохранять её при idle-ответах. Добавить проверку «restore → несколько status polls → Play → seek на сохранённую позицию».

### 2. Ошибка импорта загрузки показывается как успешно завершённая загрузка

**Место:** [downloadModel.ts](F:/Spotify-Like/src/downloadModel.ts:77), [App.tsx](F:/Spotify-Like/src/App.tsx:38), [DownloadManager.tsx](F:/Spotify-Like/src/DownloadManager.tsx:28).

Backend возвращает отдельные результаты `file_not_found`, `ambiguous`, `invalid_file`, `import_failed`. Frontend вызывает callback, который обновляет библиотеку только для двух успешных результатов, а затем отмечает любую финализацию завершённой. Негативные результаты нигде не сохраняются для отображения. Менеджер продолжает показывать состояние передачи «Завершено».

**Доказательство:** mock API возвращает `status: import_failed`; `DownloadSession.error` остаётся пустым, состояние записи — `completed`.

**Последствие:** файл может не появиться в библиотеке, а пользователь не узнает причину. Неоднозначный выбор файла и отсутствие файла также проходят без объяснения.

**Исправление:** отдельно показывать результат передачи и импорта. Сохранять результат финализации, отображать причину и действие для исправления, не трактовать все ответы как успешный импорт.

### 3. Временная ошибка финализации загрузки не повторяется

**Место:** [downloadModel.ts](F:/Spotify-Like/src/downloadModel.ts:54), строки 74–79.

После получения `completed` запись исключается из будущих опросов: они выбирают только `queued` и `downloading`. Если IPC финализации или обновление библиотеки завершились исключением, запись не попадает в `finalized`, но повторный вызов всё равно не происходит. Кнопки повторного импорта нет.

**Доказательство:** после одного отказа финализации два следующих вызова `poll()` оставляют число попыток равным 1.

На backend [slskd_finalize.rs](F:/Spotify-Like/src-tauri/src/services/slskd_finalize.rs:189) также сохраняет негативные результаты финализации в кэш. Простое добавление кнопки без изменения политики повторов не решит сценарий, когда файл появился позже первоначального `file_not_found`.

**Исправление:** иметь отдельную очередь незавершённых импортов, ограниченный повтор временных ошибок и явное ручное повторение. Пересматривать временные отрицательные результаты backend, сохраняя идемпотентность успешного импорта.

### 4. Сохранение сессии проверяет весь каталог на диске под блокировкой записи SQLite

**Место:** [playback_session.rs](F:/Spotify-Like/src-tauri/src/playback_session.rs:127), [player.tsx](F:/Spotify-Like/src/player.tsx:114).

Каждые примерно пять секунд воспроизведения вызывается сохранение. Оно начинает `TransactionBehavior::Immediate`, выбирает **все** треки библиотеки и вызывает `Path::is_file()` для каждого. Затем полностью переписывает очередь. Проверка не ограничена треками сохраняемой сессии.

**Риск:** большая библиотека, сетевой диск, медленный внешний накопитель или недоступный путь могут надолго задержать операцию и конкурирующие записи лайков, импорта и плейлистов. `persistChain` последовательно накапливает сохранения, если каждое выполняется дольше интервала. Точная длительность на пользовательской библиотеке не измерялась; структура затрат и удержание write-транзакции подтверждены исходным кодом.

**Исправление:** проверять только нужные ID; вынести файловые проверки из write-транзакции; обновлять позицию отдельно от изменения очереди и объединять устаревшие pending snapshots.

### 5. Локальный поиск не находит сочетание исполнителя и названия

**Место:** [libraryModel.ts](F:/Spotify-Like/src/libraryModel.ts:14).

Полный запрос должен быть подстрокой одного поля: `title`, `artist` или `album`. Слова не ищутся по совокупности полей, внутренние повторные пробелы не нормализуются; `album_artist` и `genre` не участвуют.

**Доказательство:** трек с исполнителем «Ёлка», названием «Ночь», альбомом «Город» находится по «Ночь», но не находится по «Ёлка Ночь» и «Ночь Город». Существующий `frontend-regression.mjs` ожидает подобный поиск и падает уже на первой проверке.

**Последствие:** привычный запрос «исполнитель название» даёт пустую локальную выдачу при наличии файла. Это функциональное ограничение текущей реализации; отсутствие поиска по жанру само по себе может быть продуктовым выбором.

**Исправление:** нормализовать пробелы и проверять все токены по объединённым разрешённым полям. Зафиксировать ожидаемую семантику поиска тестами.

### 6. Установленная версия автоматически пытается импортировать `F:\Music`

**Место:** [main.rs](F:/Spotify-Like/src-tauri/src/main.rs:434), [App.tsx](F:/Spotify-Like/src/App.tsx:128).

У обычной сборки источник по умолчанию жёстко задан как `F:\Music`. При отсутствии подключённых папок приложение запускает сканирование этого пути. На другом компьютере это даёт ошибку при первом запуске. Если пользователь убрал последний источник, после перезапуска он может добавиться снова; отсутствие источников не отличено от самого первого запуска. Portable этого дефекта не имеет.

**Подтверждение:** анализ прямого пути `default_scan_folder → startup effect → scan_folders`; на чужой машине не воспроизводилось.

**Исправление:** на первом запуске предложить выбрать папку либо использовать существующую системную папку Music. Хранить признак прохождения первого запуска и уважать сознательное удаление последнего источника.

### 7. Ответ поиска текста старого трека может скрыть поиск текста нового трека

**Место:** [App.tsx](F:/Spotify-Like/src/App.tsx:159), условия кнопки в строке 326.

Автоматическая загрузка текста имеет `alive`-защиту, а ручной `fetchLyrics()` — нет. Можно запустить поиск для A, перейти на B и получить поздний ответ A. Он записывает `lyrics` и статус независимо от текущего трека. Рендерер правильно фильтрует текст через `lyricsForTrack`, поэтому чужие слова не должны показываться, однако кнопка «Найти текст» проверяет необработанный `!lyrics`. Чужой ненулевой документ скрывает кнопку для B, а badge источника также берётся из сырого документа.

**Подтверждение:** анализ асинхронного пути и условий отображения; живой запрос с управляемой задержкой не запускался.

**Исправление:** проверять ID трека и номер запроса перед применением результата. Для badge и кнопки использовать документ текущего трека, а не общий `lyrics`.

### 8. Удалённый или повреждённый следующий файл останавливает автоматическое продвижение очереди

**Место:** [player.tsx](F:/Spotify-Like/src/player.tsx:115), функции `load` и `advance`.

Когда текущий трек закончился, hook заранее помечает его ID обработанным и пробует загрузить следующий. При ошибке загрузки очередь/курсор остаются прежними. Последующие опросы видят тот же ended-ID, поэтому не пробуют продвинуться снова. Пропуска недоступного трека нет. Проверка существования выполняется при восстановлении сессии, но файл можно удалить позже; повреждённый файл также остаётся в библиотеке.

**Последствие:** последовательность A → недоступный B → доступный C останавливается после A. Пользователь получает ошибку, но автоматическое воспроизведение до C не продолжается.

**Подтверждение:** анализ обработки ошибки и ended-ID; реальный аудиопереход не тестировался. Решение, должен ли плеер автоматически пропускать ошибки, следует явно закрепить как поведение продукта.

**Исправление:** ограниченно проходить оставшиеся элементы с уведомлением о пропущенных файлах; не зацикливать повтор одного повреждённого трека.

### 9. Автоматические проверки не дают надёжного общего сигнала состояния проекта

**Место:** [package.json](F:/Spotify-Like/package.json:26), [release.yml](F:/Spotify-Like/.github/workflows/release.yml:23), [Cargo.toml](F:/Spotify-Like/src-tauri/Cargo.toml:40).

- `npm test` запускает только Rust с default features, без frontend и без `slskd`/`external-lyrics`.
- Полный frontend-набор имеет 15 failures. Среди них старые английские подписи после русификации, ожидания старой структуры компонентов и прежней схемы player layout. Это не 15 доказанных продуктовых багов, но красные проверки затрудняют обнаружение новых регрессий.
- Старый queue regression не обновлён под `useCallback`, поэтому не доходит до проверки очереди.
- Без AI общий `cargo test` компилирует `phase4b_smoke` и `phase4b2_evaluation`, которые безусловно импортируют отключённый `undertone::ai`. В Cargo нет `required-features = ["ai"]` для этих примеров. Тесты `--lib --bins` проходят, поэтому это проблема test targets, а не доказательство неработоспособности portable-приложения.
- Release workflow собирает и публикует установщик, но не запускает frontend/Rust regression tests перед публикацией.

**Исправление:** единая команда проверки с frontend и Rust feature matrix; актуализировать устаревшие assertions и mock; явно ограничить AI-примеры feature-флагом; добавить обязательные проверки в CI до публикации.

## Что сделано разумно

- Схема SQLite мигрирует транзакционно; включены foreign keys, WAL и busy timeout. Изменения коллекций используют транзакции, ошибки частичного изменения проверяются тестами.
- Большинство тяжёлых IPC-команд вынесены в `spawn_blocking`; сканирование выполняется в отдельном потоке. Прежняя проблема тяжёлой eligibility-проверки при открытии Lyrics по текущему пути не повторяется.
- slskd ограничен loopback-адресами; запрещены секреты в URL, перенаправления и proxy. Есть проверки размеров ответа, сроков поиска, ошибок авторизации и непротекания ключа в ошибки.
- Удаление трека имеет проверку назначения вне подключённой библиотеки, обработку коллизий, перенос между дисками через копирование и проверку размера, попытку rollback при ошибке БД. Эти штатные сценарии покрыты Rust-тестами. Полной атомарности файловой системы и БД при аварийном завершении процесса это не обеспечивает.
- Локальный поиск и Soulseek сохранены в одной поверхности; удалённый запрос запускается явным действием. Файловые пути удалённых результатов не используются как локальные пути напрямую.
- Списки треков и карточек виртуализированы; canvas-визуализация не заставляет React перерисовываться на каждый кадр.
- Версии package.json, Cargo.toml и tauri.conf.json согласованы: 0.2.5. Подписанное обновление настроено; корректность реальных release assets и установленного EXE в эту проверку не входила.
